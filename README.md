# macos-display-keepawake

让 MacBook **合盖 + 外接显示器** 的场景下，远程桌面不再隔一段时间就卡在「正在传输画面」。

一个 LaunchAgent + 系统电源断言，不用装任何第三方 App，不改任何系统管理策略，一条命令可卸载。

---

## 症状

- 笔记本合盖放在家里/公司，外接显示器接着，电源接着。
- 隔了一段时间（比如几小时、过夜）用手机远程连回来。
- 客户端一直停在「正在传输画面」/「加载画面」，等很久也出不来。
- **退出再进一次，往往就正常了**。之后再连也基本正常，直到下一次长时间闲置。

这不是网络问题，也不是没充电。日志会告诉你真相。

## 根因

远程软件（UU 远程、向日葵、ToDesk、Parsec 等基于 macOS ScreenCaptureKit 的实现）在被控端启动采集时，是**视频和系统声音一起启动**的：

```
08:53:43  远程软件请求唤醒显示器，系统记录 Display is turned on
08:53:44  请求启动一个同时包含画面和声音的 ScreenCaptureKit 流
08:53:45  系统为该流创建 AudioTap（系统音频采集设备）
08:53:45 → 08:56:21  该 AudioTap 的 IO 线程连续 11 次启动失败，
                     每次卡满 14.02 秒，期间处理到的音频帧为 0
08:56:21  音频终于启动成功，视频流随后也跟着起来
```

关键点：**视频管线本身没有报错，是音频采集把它一起拖住了。** 音频起不来，视频就不发首帧，手机端就一直显示「正在传输画面」。

日志里的signature长这样（`replayd` 与 `coreaudiod`）：

```
coreaudiod  HALS_IOContext_Legacy_Impl::StartIOThread: got an error from starting the IO thread, Error: 0x3C
replayd     HALC_ProxyIOContext::IOWorkLoop: the server failed to start, Error: 0x3C
```

### 为什么「重进就好」

第一次连接把**冷启动的代价**付掉了（那 2 分 35 秒）。你重进时，音频设备、`replayd`、显示器管线都已经是热的状态，所以秒开。

**这说明它不是随机故障，而是一次性的首次激活成本。**

### 为什么合盖 + 外接屏更容易触发

- macOS 会按空闲计时器让显示器休眠（企业设备上这个时间常被 MDM 描述文件锁定，改不了）。
- 显示器休眠/唤醒时，系统会**重新枚举音频设备**。而很多外接显示器（尤其是 USB-C / DisplayPort 的）本身就是一个 DP 音频输出设备，一睡一醒就是一次设备上下线。
- 如果同时还有蓝牙耳机在断连/重连、默认输出在「内置扬声器 / 显示器音频 / 耳机」之间跳，音频拓扑会持续抖动。
- 远程软件恰好在这时启动「视频+音频」采集，就撞上了这个窗口。

## 方案原理

不去修厂商的代码，也不去改 MDM 策略，只做一件事：

> **让显示器永远不睡。**

用 macOS 官方的电源断言 `PreventUserIdleDisplaySleep`（`caffeinate -d` 持有的就是它）。这是系统提供的、给「正在放视频/演示」这类场景用的正规机制，优先级高于任何空闲计时器。

显示器一直醒着 → 远程软件连进来时**没有唤醒事件** → 不会重新枚举音频设备 → 采集流毫秒级启动。

顺带一提：**不要用「定时动一下鼠标」那种假激活**。它会打断你正常使用，还会和远程软件自己的唤醒逻辑打架。电源断言才是正确做法。

## 安装

```bash
git clone https://github.com/owenweng0101/macos-display-keepawake.git
cd macos-display-keepawake
./install.sh
```

默认模式下，装完即生效，开机自动启动，不需要 sudo。

### 两种模式

| 模式 | 行为 | 适合 |
| --- | --- | --- |
| 默认 | 显示器**始终**不休眠 | 电脑长期插电、放在固定位置当被控端 |
| `./install.sh --lid-only` | 只在**合盖**时保持唤醒，开盖后恢复系统正常休眠 | 日常还要拿它办公、在意电池和屏幕寿命 |

```bash
./install.sh --lid-only
```

## 验证

```bash
./status.sh
```

关键看两行：

```
=== 电源断言 ===
   pid 50905(caffeinate): ... PreventUserIdleDisplaySleep named: "caffeinate command-line tool"

=== 显示器空闲计时器 ===
   displaysleep  30  (display sleep prevented by caffeinate)
```

计时器还是 30 分钟（策略没被改），但**已经被断言压住**，显示器不会睡。

你也可以直接盯系统日志，看修复前后的差异：

```bash
/usr/bin/log show --last 1h --predicate 'process == "replayd"' --style compact \
  | grep -E "startAudioSession|Error: 0x3C"
```

修复前：`Error: 0x3C` 连续出现，每次间隔约 14 秒。
修复后：连接时直接 `audioDidStart=1`，没有 0x3C。

> 注意：zsh 里 `log` 可能被别的函数/别名占用，用完整路径 `/usr/bin/log`。

## 卸载

```bash
./uninstall.sh
```

立即恢复系统原本的休眠行为，不残留任何文件。

## 边界：它能解决什么，不能解决什么

**能解决**

- 合盖/闲置一段时间后，第一次远程连接卡在「正在传输画面」。
- 显示器已经睡过、采集服务被系统回收过之后的重连。
- 不止 UU 远程，所有走 ScreenCaptureKit 的远程桌面/录屏软件都适用同一机制。

**不能解决**

- **显示器被物理断电或拔线**：系统里没有可采集的画面源，任何保活都无效。这种场景需要创建虚拟显示器（如 BetterDisplay）。
- **音频路由持续抖动**（例如蓝牙耳机反复断连重连）：断言只能消除「显示器休眠」这一个触发源，音频设备仍可能因为别的原因重新枚举。可以配合在客户端关闭「播放被控端声音」，让采集不依赖系统音频。
- **远程软件自身的首帧/重连逻辑 bug**：那部分只能在客户端或厂商侧解决。
- **重启后未登录**（FileVault 预启动阶段）或**电脑已关机**：任何软件方案都无能为力。

## 取舍

- 显示器会**常亮**。默认模式下，你人在电脑前时屏幕也不会自动熄（锁屏/屏保仍正常触发）。介意的话用 `--lid-only`。
- **电池供电时同样生效**，4K 屏 + 采集的耗电不低，不建议长时间纯电池无人值守。
- **热量**：合盖没有风道，长时间高负载会降频，属预期。
- 电量极低时系统仍会强制休眠，这是固件级保护，`SleepDisabled` 也拦不住。

## 原理相关的两个细节

**为什么 MDM 锁不住它？**
MDM 描述文件锁的是「空闲多久关显示器」这个**数值**，而电源断言是「有进程正在使用显示器」这个**状态**。两套机制，互不覆盖。所以本方案不需要、也不会修改任何管理策略。

**为什么系统设置里那个 30 分钟改不了？**
被描述文件托管。本方案不碰它，只在它之上加一层断言。

## 实测环境

- MacBook Air (Apple M4)，macOS 26.7.1 (25G241)
- 外接 4K 显示器，USB-C 连接并反向充电，合盖使用
- UU 远程 4.44.0（被控端）
- 复现时：`AudioDeviceStart` 每次超时 14.02 秒 × 11 次，合计约 2 分 35 秒

不同 macOS 版本、不同远程软件的日志字段可能不同，但 `PreventUserIdleDisplaySleep` 这个机制从很早就存在，行为一致。
